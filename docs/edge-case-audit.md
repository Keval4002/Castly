## 2. Top risks

1. **Work runs inside the web request, with no sweeper (JB-01, JB-03, JB-07, JB-11). Verified.** `POST /api/generations` runs `after(() => runGeneration(...))` with `maxDuration = 300` (`src/app/api/generations/route.ts:10,18`). `vercel.json` has no crons. A killed or timed-out function leaves the job running and the credits locked until that same user next polls. The README's claimed 10-minute reaper does not exist as a scheduled job.
2. **No idempotency on job or order creation (UP-09, JB-06, PM-04). Verified.** A double-tap, second tab or retry creates two generations and two debits, and every payment click creates a new Razorpay order.
3. **The fidelity gate fails open and measures little (QA-01, JW-01, JW-02, CL-01 to CL-04). Verified.** The gate is one vision-LLM judge on a downsized preview. If every judge errors, the image is delivered as "unverified" and counted as passed (`src/lib/image/quality.ts:51`). There is no colour distance, SSIM, OCR, stone count or anatomy check, so the 5% and 3% targets cannot be measured today.
4. **Kids' clothing policy is not implemented (CL-12, LG-03). Verified for the options.** Kidswear and child-model casting are live options (`src/lib/catalog/options.ts:127,152`). There is no hold or review state, so child-model images are delivered automatically, against the locked manual-review decision. Smallest interim fix: block child models server-side until review exists.
5. **iPhone HEIC and corrupt uploads return HTTP 500 (UP-01, UP-07). Verified.** `normalizeUpload` has no error handling (`src/lib/image/process.ts:21`), and this install's sharp only decodes AVIF through its HEIF loader, so HEIC fails. Many of your users are on iPhones.
6. **No cost controls or kill switch (CO-01, CO-02, CO-05, CO-09).** The rate limiter is an in-memory Map per serverless instance, so it is effectively off on Vercel. Uploads call paid classify and background-removal services without charging credits. The signup bonus (10 credits) is farmable. There is no spend alarm or emergency stop.
7. **Margin leaks on retries (CO-05, CO-06, PV-11).** Retried and discarded attempts, judge calls and fallback calls are not recorded or charged. The audit-D estimate puts a Premium image needing one retry at roughly Rs 51 of cost against about Rs 27.5 of revenue. That figure is the agent's estimate from `docs/PRICING.md` and should be confirmed.
8. **No privacy, terms, support or deletion (SC-07, SC-09, LG-02, LG-07, PM-03).** There are no `/privacy` or `/terms` pages, no support contact, no asset or account deletion, and no training-consent record. That is a DPDP exposure and leaves a paid user with nobody to contact when something fails.
9. **Payments have no reconciliation (PM-02, PM-03). Verified for the helper.** There is no reconciliation job, refund or chargeback handling, or `callback_url`. `assertProductionReady` is referenced in a comment in `src/lib/env.ts` but is never defined, so production config is not actually validated at startup.
10. **No observability (OB-01 to OB-04, SC-12).** There is no error tracking, funnel, alerting or failure taxonomy, and no security headers. A production failure would go unseen.

2. UP-09: no idempotency on POST /api/generations; each retry debits credits.

# Audit B: JW / CL / QA / LG (working tree on disk)

### Headline finding: what "fidelity" actually is
`src/lib/image/fidelity.ts` is a **single vision-LLM judge** (fidelity.ts:63-100). No colour-distance, no mask, no SSIM, no OCR, no stone-count, no anatomy classifier, no NSFW classifier. The judge lists 4-8 "features" from the reference, marks each match/changed/missing (fidelity.ts:33-41), and `scoreVerdict` (fidelity.ts:48-60) takes min(LLM score, checklist ratio). `passes()` (quality.ts:137) requires sameProduct, score >= 0.8 (env.ts:65) and prominence hero/clear. The only deterministic image maths in the repo is `repairMask` (prepare.ts:105), which is input prep, not output QA.
Consequences:
- No quantitative measurement of any kind. An "I'd say the metal looks similar" judge passes drift of several dE.
- Judge sees 640px reference / 896px output JPEG previews (fidelity.ts:19-20), so fine detail (stone count, hallmarks, small print) is below its resolution.
- Judge is non-deterministic and unlogged (no eval set). The <=5% jewellery / <=3% clothing visible-failure target has no measurement or harness. Nothing counts failures.
- Fail-open: if every judge errors/unavailable, `judgeFidelity` returns null and the image is delivered as `verified:false, passed:true` (quality.ts:151, service.ts:263-266 only blocks when `verified`). Outage of the judge = zero QA, silently.
- `FIDELITY_MODE` defaults to enforce, but `flag`/`off` deliver unverified.
- Category is never passed to the judge: prompt is the same for jewellery and clothing. No category-specific checks (chain, pairs, anatomy, sleeves).

Locked decision "different model per image": `generateWithFallback` (router.ts:352-369) uses the same chain head for every variant; variant index is only a seed hint. Not implemented (belongs to routing, noted under QA-10).

### How a generation actually runs on Vercel
1. `POST /api/generations` (src/app/api/generations/route.ts:12-22) auth + in-memory rate limit (20/min per instance, api.ts:63) -> `createGeneration` inserts `generations` row (status queued) + N `generation_images` rows + debits credits in ONE transaction (service.ts:83-112, ledger key `generation:<id>`). Returns 202 with the DTO immediately.
2. Work is scheduled with `after(() => runGeneration(gen.id))` (route.ts:18). There is no queue and no worker. The heavy work (LLM prompt plan, N parallel image-provider calls, sharp post-process, fidelity judge LLM, retry, asset save) executes inside the SAME serverless invocation, via waitUntil, capped by `maxDuration = 300` (route.ts:10). Per Next docs (after.md:50) `after` only lives for the route's max duration. Whether 300s is honoured depends on the Vercel plan (Hobby is lower). vercel.json has only `framework` (no crons, no function config).
3. `runGeneration` claims the job with a conditional UPDATE queued->running (service.ts:137-142): double-run protected, but there is NO heartbeat or lease.
4. All variants run via `Promise.all` (service.ts:173) with no concurrency limit (MAX_VARIANTS=4). Each variant calls `generateFaithfully` (service.ts:238): up to `GENERATION_MAX_ATTEMPTS` (default 2, env.ts:67) x `generateWithFallback` over a 3-provider chain (router.ts:44-61). Per-provider timeouts are 90/120/180s (aisdk.ts:66-98) and `maxRetries: 1` in the AI SDK call (aisdk.ts:35) can double them. Worst case is far beyond 300s; typical happy path is fine.
5. Polling: client `useGenerationPolling` hits `GET /api/generations/[id]` every 1.5s while active (usePolling.ts:12-37). No backoff, no ETA, errors are swallowed (`Promise.allSettled`, failures ignored, loop continues forever while the tab is open).
6. Timeout/crash: if the invocation is killed at 300s, nothing runs a catch/finally. Images stay `pending`, the generation stays `running`, credits stay held. Recovery is ONLY lazy: `getGeneration` (service.ts:411) and `listGenerations -> reapStaleGenerations` (service.ts:310, 420) call `finalizeGeneration` once `createdAt` is older than 10 min (STALE_AFTER_MS, service.ts:23). Pending images become failed "Timed out" and are refunded idempotently (`refund:<id>`, service.ts:278-296). There is NO cron/sweeper: a user who never returns keeps credits locked and the row `running` forever; `reapStaleGenerations` is scoped to one user. Stale detection uses `createdAt`, not last progress.
7. State machine: DB enums `generation_status` (queued/running/succeeded/partial/failed) and `image_status` (pending/succeeded/failed) exist; transitions are guarded in two places only (claim UPDATE service.ts:140; finalize UPDATE `inArray(status, [queued,running])` service.ts:306). Per-image UPDATEs (service.ts:176-218) have no status guard, so a straggler could flip a reaped "failed" image to "succeeded" after the refund (double benefit). Low likelihood because the invocation is hard-killed first, but not enforced.
8. Cost/versions: per image `provider`, `model`, `prompt`, `latencyMs`, `attempts`, `fidelity` stored (schema.ts:143-153). NOT stored: seed (none passed; `variant` is documented as seed but no provider uses it, types.ts:8), provider cost, tokens, prompt-LLM id/model per image, judge model beyond `fidelity.judge`, retried/discarded attempts' provider+cost, fallback `attempts[]` list from the router (returned in RoutedResult but dropped at service.ts:200-212).

### Most dangerous gaps (ranked)
1. No sweeper/heartbeat: killed invocations leave credits locked until the owner returns (service.ts:309-322); `createdAt`-based, per-user only.
2. Worst-case job time (3 providers x 90-180s x SDK retry x 2 fidelity attempts, all variants parallel) exceeds the 300s maxDuration; no job deadline budget, so crashes are likely under any provider slowness (JB-03/11).
3. No POST idempotency key: double-submit = double job + double charge (JB-06).
4. No circuit breaker/Retry-After/global concurrency; router ignores `retryable` and falls through on policy refusals (JB-04, PV-02, PV-04).
5. No per-call cost/usage recording; margin and retry budget unknowable (PV-11).
6. No seed/params/prompt-LLM/model-version metadata (SET-07) and no provider data-retention register (PV-05).
7. Unguarded per-image UPDATEs could resurrect a reaped image after refund (JB-08).
8. No cancel, no per-image regenerate, no zip/platform presets/Web Share (JB-09, SET-06, MK-01/04/07).

Problems the doc does not model:
- **Fidelity retry is on by default** (`FIDELITY_MODE=enforce`, `GENERATION_MAX_ATTEMPTS=2`, `env.ts:64,67`). Every retried image costs 2 generations. Premium with one retry = ₹51 vs ₹27.5 revenue, a loss of about ₹23.5 per retried image. Quick with one retry = ₹5.2 vs ₹3.44 (loss), Studio = ₹6.8 vs ₹6.88 (break-even). The retry rate is not logged as cost, so the true margin is unknown. Break-even retry rate on Premium (Business pack) is about 8%; on Quick about 0% retries on the fallback.
- **Retry-then-refund**: if both attempts fail the judge, revenue is ₹0 and cost is 2× generation + 2× judge. Premium worst case about ₹51 lost per image, with the user able to repeat it.
- **Uncounted per-job costs**: the fidelity judge (Gemini 3.5 Flash, vision, one call per attempt), the upload classifier (vision LLM), BiRefNet background removal on fal (every upload, even when never generated), and the prompt LLM (counted at ₹0.04). PRICING.md only counts the last one.
- **Fallback chain**: a failing primary may still bill. Premium falls back to Gemini (cheaper), so fallback helps; Quick falls back to a costlier model (Gemini ₹3.4 = 0% margin).
- **Premium at 8 credits is ~7% (single attempt)**; the doc itself recommends 10 credits (₹34.4, 26% margin single attempt, ≈ break-even at one retry) or routing Premium to Nano Banana Pro (₹13.2) / gpt-image-1 medium (₹8). `pricing.ts:38` is still 8.
- **Signup bonus**: 10 credits = up to 1 Premium (8 cr, ₹25-51) + 2 Quick, i.e. a worst-case acquisition cost of about ₹30-55 per free account vs the doc's ₹17-26 (which assumed Studio). Free credits with farmable accounts (CO-02) make this the main money leak. Failed (refunded) images keep returning credits, so one free account can cost far more than ₹55.
- Pack gross ₹/credit (4.98 / 4.54 / 4.16) pass the doc's own ≥ ₹4 Business rule, but net after GST + Razorpay is below Quick provider cost on the Gemini fallback.

### Other observations
- `finalizeGeneration` (`service.ts:273-307`) is not a single transaction: refund (idempotent) then status update guarded by `inArray(status, [queued, running])`. A crash in between is safe because both steps are idempotent. A late-finishing runner can still write `succeeded` images after the reaper has failed and refunded the job (`service.ts:201-212` has no status guard), giving a user free images; this is only reachable if a job exceeds the 10-minute stale limit (Vercel `maxDuration` 300 prevents it, self-hosting does not).

- `SESSION_SECRET` default is public and not rejected in production (`env.ts:22`); it only signs local-storage URLs and dev sessions, which are blocked in prod, so low impact today, but a trap for later.
- Tests cover ledger atomicity and payment race on a real DB (`credits.test.ts`), but no tests for the webhook route signature/handler, order creation idempotency, or reaper-vs-runner races.

## 4. Architecture observations (sections 11 to 13 of the edge-case spec)

- **Jobs.** One web function does everything: debit, insert, `after()` to run all variants in an unbounded `Promise.all`, judge, retry, refund. There is no queue, lease, heartbeat, dead-letter or state machine, and the per-image UPDATEs are not status-guarded. This violates JB-01, 03, 07, 08, 11 and 12. On Vercel with no worker the realistic path is one job row per shot, a short-lived worker route per shot, and a cron sweeper. That is Phase 1.
- **Storage.** Behind a single `Storage` interface with local and Supabase drivers (`src/lib/storage/index.ts`), keys are server-generated (`u/<user>/<folder>/<uuid>.jpg`), URLs are signed on read with a 1-hour TTL, and no hard-coded Supabase URLs were found. This is a good starting point for the R2 migration. Gaps: no delete method, no lifecycle rules, and no direct-to-storage presigned upload (uploads buffer the whole body in the route, and Vercel's 4.5 MB request limit is below the 8 MB cap).
- **Credits.** Debit is up front inside the same transaction as the job insert, with per-image refund on failure. The ledger is atomic and tested (PM-05). It is not reserve/commit, and retries, judge and classifier costs are absorbed. The kickoff note says not to change pricing or credits logic except for per-shot accounting, so the per-shot reserve/commit change needs your sign-off.
- **Providers.** One interface with a tier-based fallback chain, which is good. But the router falls through on every error (it ignores `ProviderError.retryable`, so policy refusals are retried on other vendors), has no backoff, circuit breaker or `Retry-After` handling, no cost or usage recording, no stored seed or model version, and passes no seed to any provider.
- **Dev auth.** `dev-login` is gated by `AUTH_PROVIDER=dev`, and `env.ts` blocks dev mode in production unless `ALLOW_INSECURE_DEV_MODE` is set. `SESSION_SECRET` has a public default that is not rejected in production (audit D, not independently verified).

## 5. Cost observations

- Retries: fidelity retry is on by default (`FIDELITY_MODE=enforce`, two attempts). Failed-twice images are fully refunded but still cost provider spend, so one account can repeat this at no cost to itself.
- Fan-out: all variants run concurrently with no global concurrency cap and no per-job deadline.
- Fallback: a dead vendor's full timeout (90 to 180 s) is paid per variant before falling through.
- Preprocessing: classifier, background removal and judge calls are not in `docs/PRICING.md`, and uploads trigger them without charging credits.
- Premium: 8 credits per image (the kickoff note says 10, so `docs/PRICING.md` or the note is out of date and needs reconciling) at about 7% margin per audit D.
- Large images: uploads are capped to 2048 px and normalised before use, which is sensible. Output sizes sent to the judge are downsized.
- Unbounded sets: count is capped at 1 to 4 today, but the planned shot-fan-out needs an explicit per-set cap and estimate (SET-10, CO-04).
